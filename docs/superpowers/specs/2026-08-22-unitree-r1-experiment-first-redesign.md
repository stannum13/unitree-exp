# Unitree R1 Experiment-First Prompt Redesign

**Date:** 2026-08-22  
**Status:** Approved design, pending prompt implementation  
**Primary prompt:** `Unitree R1 Codex Prompt.md`

## Objective

Redesign the autonomous Unitree R1 program so that executed experiments and measured evidence are the primary outputs. The first paid gate establishes headless Isaac Sim on Google Cloud from an Apple M2 Max client. A bounded R1 port is then attempted using Unitree's official R1 MuJoCo model as the embodiment source. If that port cannot reach a trustworthy reset/step baseline within its resource gate, the program immediately uses the official R1 MuJoCo stack as the experimental substrate.

The redesigned prompt retains the ambition of E1 through E6. It removes incentives to create broad scaffolding, placeholder runners, interfaces, or reports that are not consumed by an executed experiment.

## Authority and precedence

When instructions conflict, apply this order:

1. Explicit user instruction.
2. Physical safety and the prohibition on physical robot control.
3. The absolute USD 30 cloud-spend ceiling.
4. Preservation of existing user resources and changes.
5. Measured evidence and accurate status reporting.
6. Experimental gate order and stopping rules.
7. Required experiment ambition.
8. Documentation, organization, and polish.

Measured artifacts override narrative claims. A later section may refine an earlier instruction but may not relax a higher-precedence constraint.

## Evidence-first operating rule

A file, module, test, interface, configuration, report, or dataset schema has no independent value in this run. Create it only when it is required to execute the next open experimental gate or preserve measured evidence.

An experimental gate is not successful merely because code:

- imports or compiles;
- passes unit tests;
- emits synthetic output;
- exposes a runner or configuration;
- converts an asset;
- creates a checkpoint without evaluation rollouts; or
- generates a report.

Scientific success requires nonzero simulator rollouts, predeclared metrics, real exit status, immutable provenance, and evidence generated by the selected R1 simulation substrate.

The large suggested source tree in the current prompt will be removed. Paths emerge from executed gates and existing upstream conventions. Empty placeholder modules, placeholder reports, and unrun experiment runners are forbidden.

## Hard cloud-cost envelope

USD 30 is an absolute ceiling, not a target. It means incremental, program-attributable GCP list-price spend before tax and currency conversion. Unrelated pre-existing project usage is excluded from the experiment ledger and must not be modified. The live price must be queried before provisioning.

The design-time envelope uses the higher on-demand rate even if Spot is selected. Using unrounded prices observed on 2026-08-22:

| Resource | Conservative bound |
|---|---:|
| `g2-standard-8` compute | USD 0.853624312/hour |
| 150 GiB `pd-balanced` | USD 0.020548500/hour |
| Ephemeral external IPv4 | USD 0.005000000/hour |
| Conservative combined runtime rate | USD 0.879172812/hour |
| Maximum charged runtime | 24.000 hours |
| Maximum runtime cost | USD 21.100147488 |
| Bounded non-runtime reserve | USD 5.000000000 |
| Unallocated contingency | USD 3.899852512 |

Create at most one successfully provisioned paid VM for this program. Non-billable capacity errors may select another verified zone, but once a worker reaches a billable state it is the campaign's only worker. On-demand is the default because bootstrap and cross-engine diagnosis are not initially preemption-tolerant. Spot is permitted only when the program explicitly accepts early termination; its discount must not be converted into extra runtime.

Set `--max-run-duration=23h58m` and `--instance-termination-action=DELETE`. Budget the remaining two minutes as deletion slippage, producing the 24-hour charged-runtime bound above. The boot disk auto-deletes with the VM. Do not create Local SSDs, snapshots, reusable images, load balancers, Cloud NAT, reserved addresses, or additional disks.

If live prices or the VM specification differ, compute:

```text
authorized_runtime_hours = floor_to_0.1h(
    (remaining_authorized_cost
     - fixed_incremental_cost
     - bounded_non_runtime_reserve
     - deletion_slippage_allowance)
    / conservative_all_in_hourly_rate
)
```

`conservative_all_in_hourly_rate` is the greater of the live applicable rate and the design-time on-demand rate. `fixed_incremental_cost` is the realized allocation for durable storage, logging, and expected egress within—not in addition to—the USD 5 bounded non-runtime reserve. The result must be reduced when prices rise; contingency is never converted into experimental runtime.

Before every paid launch, append to the cost ledger:

- resource name and labels;
- rate source and retrieval time;
- conservative hourly and fixed-cost estimates;
- maximum run duration;
- worst-case incremental cost;
- cumulative worst-case cost; and
- remaining authorized cost.

No resource may launch if its worst-case cumulative cost can exceed USD 30.

Before creation, require zero instances with the experiment label in `RUNNING`, `PROVISIONING`, `STAGING`, or `STOPPING`. Create no replacement or fallback VM during this program. The worker must expose a verified termination timestamp and auto-deleting boot disk. Voluntary completion must synchronize and hash-verify artifacts before early deletion. Billing alerts are supplemental; they are not treated as spend caps.

Checkpoints, ledgers, and manifests must upload every five minutes and after each checkpoint to a dedicated regional object prefix. Keep no more than the latest two checkpoints and enforce a cumulative uncompressed limit of 10 GiB. Disable versioning and soft delete for this disposable prefix and apply a seven-day lifecycle rule. A VM-side soft deadline at 22h30m stops new work, finalizes logs, verifies object checksums, and begins clean shutdown. The platform deadline is a cost-containment fuse, not the artifact-transfer mechanism. Retrieve and hash-verify durable artifacts locally before deleting their temporary cloud copies.

Bound the USD 5 non-runtime reserve as follows: at most 10 GiB WebRTC egress (USD 1.20 using a conservative Premium-tier India rate), at most 10 GiB artifact retrieval (USD 1.20), seven-day object storage and operations (USD 0.10), logging/API/rounding (USD 1.00), and USD 1.50 residual contingency. Disable verbose logging export and stop streaming when its host-side byte counter reaches the quota.

## Experimental decision tree

```text
G0 local inventory, safety lock, and mapping audit
  -> G1 stock headless Isaac Sim and Isaac Lab smoke
       -> G2 bounded R1 MJCF-to-USD port and parity validation
            -> pass: Isaac Sim is the primary experiment engine
            -> fail/timebox/costbox: official R1 MuJoCo is primary
  -> G3 minimal R1 manipulation vertical slice
  -> E1 reactive execution
  -> E2 retrigger and escalation
  -> E3 semantic memory and replanning
  -> E4 specialist RL push
  -> E5 world-model ranking
  -> E6 hierarchy ablations
```

E1 through E6 remain required ambitions. A later gate may end honestly as `NOT_RUN_BUDGET_GATE`, `BLOCKED_DATA`, or another factual status, but it must not be replaced by scaffold and called complete.

## Gate definitions

### G0: Zero-cost inventory and safety

Before provisioning:

- inventory the local workspace and existing GCP resources without modifying them;
- verify billing, L4 quota, candidate zones, current prices, and available disk quota;
- pin source repositories and record SHAs;
- preserve `PHYSICAL_DEPLOYMENT_ALLOWED=false`;
- audit the reported R1 motor-slot mapping issue;
- establish the artifact and cost ledgers; and
- render the exact VM creation specification for review in logs before executing it.

### G1: Generic headless Isaac baseline

G1 proves the cloud/runtime path independently of R1:

1. Verify the L4, driver, Docker, and NVIDIA runtime.
2. Run the Isaac Sim compatibility checker headlessly and require `PASSED`.
3. Run a stock Isaac Lab headless example.
4. Run a short Cartpole reset/step or training smoke with multiple environments.
5. Require clean startup, finite states, stable GPU memory, and a retrievable output artifact.

If G1 fails, attempt at most one materially different repair. Freeze logs and select the R1 MuJoCo fallback if the gate remains unresolved or reaches its cost/time limit.

### G2: Bounded R1 Isaac viability

The authoritative R1 source is `unitree_rl_mjlab` commit `1425b15f73bd4095f0df53709d7c389c3eb9e790`. The source is the R1 MJCF subtree plus loader behavior; the raw `r1.xml` alone is incomplete. Do not treat Unitree's G1/H1 Isaac repositories as R1 support.

G2 performs:

1. Call Unitree's `get_spec()`, compile it with the repository-pinned MuJoCo stack, serialize the resolved `MjSpec`, and write every injected asset into a self-contained relative directory.
2. Recompile that self-contained bundle without importing Unitree Python and require exact reproduction of the original compiled model.
3. Export a reference manifest covering bodies, joints, geoms, sites, actuators, topology, ordering, limits, masses, COM, inertias, home pose, gains, armature, contact masks/dimensionality, friction, solver settings, and action transforms.
4. Convert the materialized MJCF using Isaac Sim's official importer and record every importer option.
5. Explicitly apply loader-side semantics in the Isaac R1 configuration: actuator group membership, stiffness, damping, effort and armature, soft-limit factor, collision policy, home state, and per-joint action scaling.
6. Headlessly reopen the generated USD and mechanically compare it with the canonical manifest.
7. Run fixed-base, contact-free paired actuator probes.
8. Run floating-base plane reset and standing probes.
9. Run bounded one-group-at-a-time and one-joint-at-a-time actuator commands.
10. Scale through 1, 16, 64, and then 256 environments, stopping before memory pressure.

The Unitree semantic transfer must use the resolved values from the pinned source. At design time these include five actuator groups, soft joint-position factor 0.9, home base height 0.76 m, the source home-joint map, full collision policy, and action scale `0.25 * effort_limit / stiffness`. Do not hard-code remembered values without checking the pinned source.

Acceptance tolerances are separated by purpose:

- Canonical bundle versus the original Unitree `MjSpec`, using the same MuJoCo version: names, counts, types, order, and collision enablement match exactly; numeric physical properties match within absolute or relative `1e-12`.
- Isaac metadata/config versus the canonical manifest: names, counts, topology, actuator membership, action order, and collision policy match exactly; joint limits/home positions are within `1e-6 rad`; mass within `1e-5` relative or `1e-7 kg`; COM within `1e-6 m`; inertia within `1e-5` relative or `1e-9 kg*m^2`; and actuator/control values within `1e-7` relative or `1e-9` absolute.
- Forward kinematics at home and three deterministic poses within 10 percent of each joint range: per-link translation error at most 0.5 mm and orientation geodesic error at most 0.05 degrees.
- Fixed-base, contact-free, two-second identical bounded target sequence: joint-position RMSE at most 0.02 rad, maximum error at most 0.05 rad, and no effort-limit overshoot above 1 percent.
- Floating-base five-second standing probe: finite state throughout, penetration at most 2 mm, base-height drift after the first second at most 5 mm, no monotonically growing kinetic energy, and hard-limit overshoot at most `1e-4 rad`.
- One-joint direction probe: zero ordering or sign failures.

Representational tolerances are strict because both manifests describe the same embodiment. Behavioral tolerances are deliberately looser because PhysX and MuJoCo use different contact and solver implementations. Passing these probes establishes a usable experimental port, not cross-engine dynamic equivalence.

G2 passes only if:

- all expected joints and actuators are accounted for;
- ordering and command direction are explicit;
- all numeric tolerances above pass;
- resets and steps remain finite;
- home pose and bounded commands satisfy the declared probes; and
- a reproducible command and immutable artifact manifest are retrieved.

A generated USD alone is `CODE_ONLY`, not success. Permit one primary conversion attempt and at most one materially different repair. When the gate's allocated cost or time is exhausted, freeze evidence and select the official R1 MuJoCo fallback.

### G2F: Official R1 MuJoCo fallback

The fallback is a planned experimental branch, not failure of the overall program. It must first reproduce the official R1 reset/step/play path from the pinned upstream checkout before modifying the task.

The experiment report must retain the Isaac failure evidence and explain whether conversion, articulation, actuation, reset, physics, or scaling caused the fallback.

### G3: Minimal manipulation slice

Build only the smallest task necessary for the hierarchy experiment: stable stance or explicitly supported upper body, one hand or wrist site, one large object, one planar goal, privileged poses, and controller-compatible position targets.

Avoid a generic simulator abstraction. The experiment contract may carry `engine=isaac|mujoco`, asset revision, control rate, and stability mode, but substrate-specific implementation remains close to existing conventions.

G3 passes only after real rollouts demonstrate reaching or pushing and produce the metrics required by E1.

## Common experimental design

### Experimental unit

One seed block is one scene seed crossed with the applicable perturbation suite. All competing variants receive identical object poses, goals, randomization draws, perturbation times, and proposal delays. Frames, action candidates, and perturbations within one seed are clustered observations, not independent samples.

Freeze three disjoint seed lists before tuning:

- `DEV`: unrestricted tuning, never used for inferential claims;
- `SCREEN`: 11 paired seed blocks;
- `CONFIRM`: 12 new paired seed blocks opened only after selecting a contrast.

`SCREEN` is used only for selection and predictive futility. It contributes zero observations to the final efficacy posterior. `CONFIRM` is the sole inferential dataset. A combined 23-block estimate may be reported only as `COMBINED_EXPLORATORY`, never as confirmatory evidence.

### Endpoints and inference

Predeclare one primary binary endpoint per contrast. Apply endpoints lexicographically:

1. Safety and runtime invariants.
2. Primary binary outcome.
3. Continuous tie-breaker such as final error, recovery latency, action age, or regret.

Do not create an arbitrary weighted aggregate score.

Use one coherent paired Bayesian model for the binary endpoint. For each block, reduce incumbent/challenger outcomes to one of `00`, `01`, `10`, or `11`, where `01` is challenger-only success and `10` is incumbent-only success. Let:

```text
theta ~ Dirichlet(1/2, 1/2, 1/2, 1/2)
counts ~ Multinomial(N, theta)
Delta = theta_01 - theta_10
```

The symmetric Jeffreys prior has no directional preference. After observing counts, update each cell parameter by its count. Compute `P(Delta > 0)` and `P(Delta >= MES)` from this fixed model using deterministic integration. Do not mix these posterior probabilities with p-values or ad hoc bootstrap thresholds.

For ordinary modules, define the minimum meaningful effect before screening as `MES = 2/12 = 16.67` percentage points: two population-scale paired conversions in the independent confirmation panel. For compute- or complexity-heavy E4 and the full-stack E6 comparison, use `MES = 3/12 = 25` percentage points. A 12-block pilot cannot resolve smaller effects reliably, and complexity-heavy additions must buy more than an ordinary module.

### Screening and confirmation

For each screened candidate, calculate the posterior-predictive probability that a fresh 12-block confirmation panel will satisfy the final `GO` rule. Use the Dirichlet-multinomial predictive distribution and analyze every simulated future panel from the original fixed Jeffreys prior, not the screening posterior.

- Drop a candidate for predictive futility when its chance of final `GO` is below 0.10. This means the remaining spend has less than a one-in-ten chance to change the decision.
- Among non-futile candidates, select exactly one challenger per predeclared incumbent using expected `Delta`, subject to safety and mechanism-specific diagnostics.
- Screening probabilities are operational only and are not efficacy evidence.

On the 12 untouched confirmation blocks:

- `PILOT_SUCCESS`: `P(Delta > 0) >= 0.95` and `P(Delta >= MES) >= 0.50`, with all safety and diagnostic gates satisfied.
- `FUTILE`: `P(Delta >= MES) <= 0.10`.
- Otherwise: `INCONCLUSIVE`.

This rule is intentionally demanding. With ordinary `MES = 1/6`, three challenger-only wins, zero incumbent-only wins, and nine ties pass; two clean wins do not. Absence of `PILOT_SUCCESS` is never called equivalence.

### Safety disqualification

Any non-finite or out-of-limit command, unbounded recovery loop, indefinite stale-action emission, failed safe hold, or method-attributable catastrophic fall ends the rollout and disqualifies the variant from control authority. It may remain an offline or shadow result.

Zero observed unsafe events is not proof of safety. Production or physical deployment remains outside this program.

### Throughput calibration

Before opening `SCREEN`, inventory and measure every workload component at the intended parallel-environment count. Estimate:

```text
required_hours = cold_start
               + asset_or_task_initialization
               + rollout_data_generation
               + training
               + checkpoint_evaluation
               + final_evaluation
               + artifact_synchronization
               + interruption_allowance
```

Measure batched wall-clock throughput, not per-environment time. Continue calibration until the one-sided 90 percent upper bound on runtime is within 10 percent of the point estimate or calibration consumes 5 percent of the stage's provisional allowance. Ten percent is deliberately below the cost ledger's non-runtime reserve; the 5 percent limit prevents calibration from consuming the experiment. Budget using the upper bound. If a stage does not fit, reduce candidate breadth rather than breaking pairing or perturbation coverage.

## Experiment-specific rules

### E1: Reactive action refresh

Screen all four execution modes on 11 paired blocks. Confirm only the selected winner against the incumbent on 12 fresh blocks.

The primary binary endpoint is recovery from the seeded perturbation within a fixed deadline, with ordinary `MES = 1/6`. Observation-to-action age, discontinuity, and jerk are diagnostics: require the prespecified direction and no Pareto regression large enough to violate action limits, but attach no second inferential framework.

If no mode clears the efficacy gate, select the simplest Pareto-safe mode and label efficacy `INCONCLUSIVE`.

### E2: Recovery decisions

The deterministic oracle scenarios are specification checks, not inferential seeds. All must pass; stale chunks, target removal, retry exhaustion, unsafe actions, and infinite-loop prevention have zero tolerance.

Then use the common screen/confirm schedule. A block succeeds only when it makes the correct decision and recovers within the fixed deadline. Use ordinary `MES = 1/6`. Any loop, missed unsafe escalation, or retry-bound breach is automatic `SAFETY_DISQUALIFIED`.

### E3: Semantic memory and replanning

Screen M1 and M2 against M0 on 11 common blocks. Freeze one persistent-memory challenger and confirm it against M0 on 12 new blocks.

A block succeeds only when the correct-object mission completes without a stale-memory action. Use ordinary `MES = 1/6`. Wrong-object actions, stale-memory actions, tool calls, and latency remain mandatory diagnostics; any wrong-object safety consequence disqualifies authority.

### E4: Specialist RL

Use three independent training seeds. Fewer seeds cannot reveal majority seed collapse. This is an engineering robustness gate, not a population claim about training stability.

Use geometrically spaced checkpoints. Do not stop for futility before one quarter of the per-seed step budget unless numerical instability or reset failure occurs. At or after one quarter, stop a seed when two successive checkpoints show no positive paired progress and the progress slope remains non-positive. Stop the variant when two of three seeds collapse or violate stability.

Select and freeze one checkpoint using only `DEV` and `SCREEN`, then compare that fixed policy against the scripted incumbent on `CONFIRM`. Use complexity-heavy `MES = 1/4`. If two of three training seeds collapse, the specialist is `FUTILE`; a single successful seed is seed-sensitive and does not pass. The efficacy posterior is conditional on the frozen policy and does not establish population-level PPO stability.

### E5: World-model ranking

Split by rollout seed, never adjacent frames. Use three model-initialization seeds and freeze architecture and checkpoint before confirmation. Define candidate success from `DEV` before screening—for example, the selected chunk ranks in the actual top two of eight and clears the fixed task-progress threshold. Pair the learned model and WM0 on every rollout-seed block and use ordinary `MES = 1/6`.

Spearman correlation, normalized selection regret, inference latency, and privileged-feature dependence are required authority diagnostics, not extra inferential tests. Latency must fit inside the measured E1 refresh slack, and any claimed non-privileged benefit must survive removal of simulator-only features.

Privileged-only success is an upper-bound shadow result, never authority for deployment. WM2 is deferred when rendered-data infrastructure consumes more than 20 percent of E5's allocation.

### E6: Hierarchy ablation

Screen implemented A-through-I variants on 11 common blocks. Freeze one best complete stack and confirm it against A or the predeclared incumbent on 12 fresh blocks using complexity-heavy `MES = 1/4`.

Adjacent component effects and any combined 23-block summaries are exploratory. Mechanism-specific diagnostics must still show that retriggering helps stalls/displacements, replanning helps blocker/instruction cases, and memory helps stale-object cases.

World-model variants remain offline or shadow-only regardless of statistical outcome during this program.

## Adaptive experiment selection

The single worker has a 22h30m productive soft deadline. G1 and G2 together may consume at most six paid hours. NVIDIA describes a normal first Isaac installation/smoke as a sub-three-hour workflow; doubling that allowance permits one R1 conversion attempt without allowing simulator porting to consume the experiment. Unused gate time returns immediately to the experimental pool. At the cap, select R1 MuJoCo and continue on the same worker.

G3 and the E1-to-E3 dependency chain come next because later experiments consume their task, runtime, memory, and dataset evidence. After every screen or confirmation, recompute the upper-bound runtime of every feasible remaining decision.

Rank feasible next actions by:

```text
decision_value_per_hour =
    posterior_predictive_probability_of_changing_the_current_decision
    / conservative_upper_bound_runtime_hours
```

Safety prerequisites and dependency order override this score. Confirmation of a promising completed screen outranks writing or smoke-testing a later experiment. Among E4, E5, and E6, spend on the highest-information feasible decision rather than equal breadth. E1 through E6 remain required ambitions, but any gate that cannot fit before the soft deadline receives `NOT_RUN_BUDGET_GATE` rather than code-only coverage.

The campaign therefore prefers a trustworthy confirmed E1-to-E3 result over shallow, inconclusive execution of every family. It may still reach all six when measured parallel throughput permits it.

## Artifact hygiene

Every paid attempt uses an immutable run identifier containing UTC time, gate or experiment, engine, seed, and short source SHA. Write first to a `.partial` directory and finalize atomically.

Each run manifest records:

- producer command and exit code;
- source and container hashes;
- engine and asset revisions;
- configuration hash and seed;
- timestamps and billed runtime estimate;
- artifact paths, sizes, and SHA-256 hashes;
- final status and failure classification.

Top-level summaries index immutable runs and never silently overwrite them. Credentials, tokens, account data, and secrets are redacted.

Do not commit containers, caches, raw videos, large logs, rollout datasets, or checkpoints. Commit only compact manifests, source changes, and result reports suitable for review. Retrieve and hash-verify necessary artifacts before cloud-resource deletion.
